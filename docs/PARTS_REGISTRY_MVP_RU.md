# Parts Registry MVP — автозапчасти как «банкноты» (UTXO / One-Time Claim)

> English version: TBD

Этот документ фиксирует план MVP системы защиты автозапчастей от подделки на базе
GeoCoin. Деталь в реестре ведёт себя как непотраченный выход (UTXO) с двумя
состояниями: «в обращении» и «погашена/установлена». Опирается на существующие
примитивы L1: NFT-слой, сайдчейны с accounting-профилем и чекпоинтами,
`CorporateIssuerPolicy` (M-of-N), canonical metadata hash, Falcon-512,
GeographicLib (WGS84), explorer, мобильный кошелёк.

Связанные документы: [B2B_FOUNDATION_RU.md](B2B_FOUNDATION_RU.md),
[BLOCKCHAIN_CAPABILITIES_RU.md](BLOCKCHAIN_CAPABILITIES_RU.md), `adr/0001`–`adr/0004`.

## 1. Модель «банкноты»

### 1.1 Два кода на единицу товара

| Код | Где размещён | Для чего |
| --- | --- | --- |
| `unit_id` (Public ID) | QR снаружи коробки | Публичная проверка до покупки: статус, счётчик сканов, custody, risk score |
| `claim_code` (Secret) | Под скретч-наклейкой / внутри запечатанной упаковки | Однократное погашение (установка на авто) |

Генерация: CSPRNG на стороне завода, `claim_code` — 128 бит энтропии. На этикетке
секрет представлен **двумя форматами одного секрета**: QR под скретчем (мгновенное
погашение в 1 тап через Android-кошелёк/web) и текстовый дубль Base58, 20–24
символа, группировка дефисами (алфавит Base58 уже исключает 0/O/I/l; 20 символов
Base58 ≈ 117 бит — достаточно, 24 символа дают полные 128 бит). В сеть и в
базы уходит **только** `claim_hash = SHA-256("geocoin:parts:claim:v1" || unit_id || claim_code)`.
Секрет никогда не хранится оператором — восстановлению не подлежит (это корректно:
утерянный код = непогашенная «банкнота», что обрабатывается процедурой re-issue
решением mint quorum на новый unit с аннулированием старого).

### 1.2 Погашение как транзакция-«предъявление»

Целевое (вариант A, консенсусный):

- UTXO единицы на сайдчейне несёт условие spends: witness должен содержать
  `claim_code`, валидатор проверяет `SHA-256(code) == claim_hash`.
- Burn-транзакция: `input = unit UTXO`, `witness = claim_code`, опциональный
  вывод-запись с VIN. Ключ оператора не участвует: потратить может только
  обладатель кода. Backend лишь релеит транзакцию.
- Гонка клонов: первая транзакция, попавшая в цепь, выигрывает; остальные
  отклоняются. Все копии этикетки, кроме первой, видят «Код погашен <дата>,
  высокий риск подделки».

Вариант B (пилотный, без правки валидатора): веб-клиент отправляет `claim_code` в
verification backend, тот строит и подписывает burn-транзакцию. Доверие к
оператору компенсируется: транзакция релеится немедленно и видна в explorer.
Рекомендация: пилот на B, целевое состояние — A.

### 1.3 Статусы

`DRAFT → ISSUED → IN_TRANSIT → IN_STOCK → REDEEMED (+VIN)`; боковые:
`FLAGGED` (аномалия), `FROZEN` (freeze quorum), `VOID` (отзыв партии).

Инварианты валидатора сайдчейна (по образцу B2B-инвариантов L1):
уникальность `unit_id`, допустимость перехода статуса, подпись текущего
custodian'а (или preimage для burn), лимит размера батча минта.

## 2. Chain of custody

- Минт партии: `mint` quorum по `CorporateIssuerPolicy`, батч привязан к
  артикулу/заводу/датe ОТК.
- Передачи (завод → дистрибьютор → дилер): транзакции на сайдчейне, подписывает
  текущий владелец (`operations`-модель), гео-метка склада — off-chain метаданные
  по схеме canonical metadata hash (`schema_id = com.geocoin.parts.custody.v1`),
  в L1 — только хеши.
- Скан покупателем в регионе, где единица не может числиться по цепочке, =
  «серый импорт или подделка» (жёлтый/красный экран).

## 3. Детектор аномалий (до вскрытия упаковки)

Все события сканов — off-chain (verification backend), периодический хеш лога
якорится в L1 для аудируемости.

| Сигнал | Правило | Реакция |
| --- | --- | --- |
| Счётчик сканов | > N уникальных проверок за 24 ч / 7 д; сканы дилера с авторизацией не завышают счётчик | жёлтый баннер «Подозрительная активность» |
| Гео-скор | дистанция/Δt между сканами > ~900 км/ч (GeographicLib, WGS84 great-circle) | красный «Минск → Алматы за 2 ч» |
| Custody mismatch | скан вне географии текущего звена цепочки | «серый импорт или подделка» |
| Спуфинг координат | расхождение IP-гео и GPS/mob-cell, рандомизация device-id | понижение trust, флаг расследования |

Выход: `risk_score 0–100`; при подтверждении аномалии — перевод unit в
`FLAGGED` (off-chain) и `FROZEN` (on-chain, freeze quorum).

## 4. Компоненты

1. **Factory Provisioning** — батч-генерация `unit_id`/`claim_code`, хранение
   только хешей, экспорт макросов этикеток (открытый QR + secret под скретчем).
2. **Сайдчейн «units»** (accounting profile) — UTXO-состояние, custody, burn;
   чекпоинты в L1 каждые ≤5 блоков (`BATCH_SIDECHAIN_CHECKPOINT`).
3. **Verification Backend** — публичный API проверки по `unit_id`, relay
   burn-транзакций, rate limit попыток погашения (защита от brute force
   по публичному QR). Секретов не хранит.
4. **Risk Engine** — счётчики, гео-скор, кластеры; лог + периодический якорь.
5. **Клиенты**: web-проверка (PWA), Android-кошелёк (скан + «Установить на
   авто», ввод VIN), бэкофис дилера/ОТК (приём, передачи, freeze).
6. **Explorer** — публичный таймлайн единицы (минт → custody → сканы → погашение).

## 5. План MVP

| Фаза | Содержание | Результат |
| --- | --- | --- |
| 0 (нед. 1–2) | schema registry `com.geocoin.parts.unit v1` (canonical CBOR), генератор батчей + экспорт этикеток, прототип web-проверки на mock-цепи | макет этикетки и проверки |
| 1 (нед. 3–5) | минт тестового батча на testnet-сайдчейне, публичный API проверки, счётчик сканов, таймлайн в explorer | «проверь коробку» работает |
| 2 (нед. 6–8) | redeem с preimage-условием (правка валидатора сайдчейна), VIN-привязка, гео-скор v1, бэкофис дилера | полный цикл «банкноты» |
| 3 (нед. 9–12) | L1-чекпоинты, freeze-операции, мобильный кошелёк, risk v2, пайплайн печати со скретч-слоем | пилот у завода/дилера |

## 6. Угрозы и контрмеры

- **Клонирование этикетки**: первый покупатель погашает; остальные видят
  «погашена» + высокий счётчик сканов.
- **Копия secret под скретчем**: возможна только при физическом доступе; гонка
  разрешается порядком транзакций в цепи.
- **Brute force `claim_code` по известному `unit_id`**: 128+ бит энтропии,
  rate limit и lockout на backend.
- **Сговор дилера (перепродажа «до погашения»)**: custody mismatch по региону.
- **Компрометация backend**: там только хеши; ключи policy в HSM; подделать
  spend без кода нельзя (вариант A).
- **Компрометация ключа policy**: recovery quorum меняет роли
  (`CARD_UPDATE_POLICY`-аналог), статусы единиц сохраняются.

## 7. Принятые решения

1. **Формат кода под скретчем — оба**: QR (погашение в 1 тап) + текстовый дубль
   Base58, 20–24 символа, группировка дефисами, без 0/O/1/I/l. Оба кодируют
   один и тот же 128-битный секрет.
2. **VIN — только хеш** (HMAC/солёный SHA-256). Открытый VIN — нарушение
   GDPR / 152-ФЗ: по VIN пробивается владелец и история. Доказательство
   «деталь стояла на этом авто» — по предъявлению техпаспорта через заводской
   backend. ⚠️ Каверзa: `claim_code` публикуется в witness при погашении,
   поэтому ключ/соль для VIN-хеша **не может** быть производной от
   `claim_code` или храниться в цепи — offline brute force по известной
   модели/году иначе реализуем. Соль держится off-chain у заводского backend
   (или ключ HMAC в HSM).
3. **Backend эксплуатирует завод**; выпуск — на учётном сайдчейне; fee за
   транзакции единиц платит заводской кошелёк.
4. **Юридическая значимость (УКЭП) не требуется**, но в якорь L1 сразу
   закладывается «доказательная готовность» арбитражного уровня: checkpoint +
   `metadata_hash` (canonical CBOR, schema registry) + хеш решения backend —
   этого достаточно для B2B-споров.
5. **Пилот — Porsche, 1 000 000 единиц.** Масштаб определяет требования:
   - минт партиями через корень Меркла: в цепь идёт `batch_id` + `batch_root`,
     а не транзакция на каждую единицу (MAX_BATCH ~10 000 → ~100 батчей);
   - provisioning должен проштамповать 1M `claim_hash` без утечки сырых кодов;
   - чекпоинты сайдчейна в L1 — по расписанию (≤5 блоков), объём anchoring
     зависит от числа custody-событий, а не от числа единиц;
   - пайплайн печати 1M этикеток со скретч-слоем — отдельная задача (2 источника:
     тиражная печать + локальный принтер для дозаказов).

Пороги risk engine (п. 5 исходного списка) — калибруются на данных пилота.
